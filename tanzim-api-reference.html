1. About This Document

This reference covers the four core REST APIs that power the Tanzim Taxi Dispatch Platform: Trip Management, Driver & Vehicle Management, Real-Time Telemetry, and Fare Pricing. Together they orchestrate the complete lifecycle of a taxi dispatch operation — from a passenger booking a ride through to fare settlement, driver shift management, and fleet compliance.

The platform is built on an event-driven microservice architecture. Each API runs as an independent service. Domain events propagate automatically across services as trips move through their lifecycle states — no manual cross-service calls are required from client applications.

4. Trip Management API

Base URL: http://localhost:10005

The Trip API is the central orchestrator of the Tanzim dispatch lifecycle. Every ride on the platform — whether booked immediately, scheduled in advance, or set up as a recurring daily commute — originates here. The service accepts booking requests from passenger apps, coordinates driver search and assignment through the Telemetry Service, tracks each trip through its progression from request to completion, submits the actual route to the Pricing Service for final fare calculation, and signals downstream services to trigger payment processing and driver performance updates.

The Trip Service does not communicate directly with drivers or passengers — it publishes domain events at every state transition, and the notification, telemetry, pricing, and driver services react to those events independently. This means a single /complete call ripples automatically into a fare calculation, a payment charge, a push notification to both parties, and an update to the driver’s behavioral score — all without the client needing to orchestrate any of it.

Trip data is the primary audit record for regulatory compliance. Every state transition is timestamped and immutable. Cancellation reasons, passenger instructions, and route coordinates are all retained for dispute resolution and government reporting purposes.

4.1. Trip Lifecycle

A trip moves through the following states from request to completion. Each transition is server-controlled — clients advance the trip by calling the appropriate lifecycle endpoint, but the platform validates that the current state permits the requested transition and rejects invalid jumps.

REQUESTED → PENDING → CONFIRMED → DRIVER_ASSIGNED
    → DRIVER_ARRIVED → IN_PROGRESS → PAYMENT_PENDING
    → COMPLETED

(pre-booking path) → SCHEDULED → CONFIRMED → DRIVER_ASSIGNED → ...

(terminal states) → CANCELLED | FAILED | EXPIRED
State What it means and what happens next

REQUESTED

The passenger’s booking request has been received and validated. The platform begins searching for an eligible driver in the vicinity of the pickup point.

PENDING

Driver search is actively underway. The dispatch engine is querying the Telemetry Service for nearby available drivers and ranking candidates. If no driver accepts within the timeout window, the trip transitions to EXPIRED.

CONFIRMED

The system has confirmed the booking is dispatchable (a driver candidate has been identified or the scheduled time is locked). For scheduled trips, the trip remains in this state until dispatch time approaches.

SCHEDULED

The trip has been pre-booked for a future date/time. No driver assignment occurs until the scheduled window opens. The trip will automatically re-enter the PENDING → CONFIRMED flow at dispatch time.

PROCESSING

The driver assignment process is executing — the platform is sending the trip offer to the candidate driver and awaiting acceptance.

DRIVER_ASSIGNED

A driver has accepted the trip. Their details are visible to the passenger. The driver is en route to the pickup location. The passenger app can now display the driver’s live position from the Telemetry Service.

DRIVER_ARRIVED

The driver has reached the pickup location and is waiting for the passenger. The pre-trip chat window (if enabled) is active. This state has a waiting timeout — if the passenger does not board within the permitted window, the driver may cancel.

IN_PROGRESS

The passenger has boarded and the trip is underway. The Telemetry Service is recording the route. The fare meter is running — actual distance and time are accumulating.

PAYMENT_PENDING

The driver has marked the trip complete. The actual route coordinates have been submitted to the Pricing Service for final fare calculation. The platform is processing the payment charge.

COMPLETED

Payment has settled successfully. The trip is closed. Both driver and passenger can now submit ratings. The driver’s behavioral score is updated.

CANCELLED

The trip was cancelled by the passenger, the driver, or the platform before completion. The reason code and timestamp are recorded. Cancellation penalties may apply depending on when in the lifecycle the cancellation occurred.

FAILED

An unrecoverable error occurred — typically a payment failure that could not be resolved. The trip record is retained for support investigation.

EXPIRED

No driver accepted the trip request within the platform’s dispatch timeout window. The passenger should retry the booking.
Clients must never attempt to transition a trip by directly setting the status field. Status is read-only in all request payloads — it is managed exclusively by server-side business logic and event handlers. Attempts to supply a status value in a request body are silently ignored.

4.4. Endpoints

4.4.1. Book a Trip

POST /api/v1/trips

Books a new ride request on behalf of a passenger. This is the entry point for all trip types on the platform. The behaviour after submission depends on the bookingType field:

  • IMMEDIATE (default): The platform begins driver search and dispatch immediately. The trip enters REQUESTED → PENDING within seconds of the call returning.

  • SCHEDULED: The booking is confirmed and held in SCHEDULED state. The platform will automatically begin driver search in the window leading up to scheduledTime. The scheduledTime field is required for this booking type.

  • RECURRING: Behaves like a scheduled trip but generates a new trip instance on each recurrence date according to recurrencePattern until recurrenceEndDate is reached. The isRecurring flag must be true and a pattern must be provided.

The fare displayed to the passenger at booking time is an estimate sourced from the Pricing Service at the moment of booking. It reflects the current zone rates, active time window, and any surge in effect. The actual fare is calculated at trip completion using the real path driven.

4.4.2. Start a Trip

POST /api/v1/trips/{tripId}/start

Called by the driver’s app when the passenger has boarded and the trip is physically underway. This is a critical lifecycle gate — the platform validates that the trip is in DRIVER_ARRIVED state before allowing the start. Transitioning to IN_PROGRESS activates route recording in the Telemetry Service: from this point forward, every GPS coordinate the driver app submits is associated with this trip and used for post-trip fare calculation.

The start timestamp is recorded as the official trip start time and is used in driver behavioral metrics (on-time rate), fare time components, and compliance reporting.

If a pre-trip chat session was open between the driver and passenger, it is automatically closed when the trip starts. No further messages can be sent during the trip.

4.4.3. Complete a Trip

POST /api/v1/trips/{tripId}/complete

Signals that the driver has delivered the passenger to the destination and the journey is over. This endpoint does more than change a status field — it submits the actual GPS path driven to the Pricing Service for final fare computation and triggers the payment collection sequence.

The actualPath parameter is an ordered array of [latitude, longitude] coordinate pairs representing the exact route driven. The Pricing Service uses this path to: measure the true distance (which may differ from the estimated route due to traffic diversions or driver decisions), detect any toll gates the vehicle passed through, and apply any zone-based rate adjustments for the areas covered.

The trip transitions to PAYMENT_PENDING immediately and then to COMPLETED once payment clears. If payment fails, the trip moves to FAILED and the support team is notified.

Table 8. Business rules
Rule Detail

Required prior state

Trip must be in IN_PROGRESS. Completing a trip that has not started returns 400

actualPath requirement

At minimum, the start (pickup) and end (drop-off) coordinates must be included. A path with fewer than 2 coordinate pairs is rejected

Fare comparison

If the actual fare deviates more than 20% above the original estimate, the platform flags the trip for review before charging. The passenger is notified of the variance

Driver identity

Only the assigned driver can complete the trip

4.4.4. Cancel a Trip

POST /api/v1/trips/{tripId}/cancel

Cancels an active trip at any point before COMPLETED. Can be initiated by the passenger, the driver, or the platform itself (e.g. dispatch timeout, safety intervention). The reason code and optional comments are permanently recorded against the trip for compliance, dispute resolution, and driver behavioral scoring.

Cancellation timing affects driver penalties: cancellations after DRIVER_ASSIGNED count against the driver’s cancellation rate in behavioral scoring. Cancellations by the platform (e.g. expired, failed) are excluded from driver metrics.

Table 10. Business rules
Rule Detail

Cancellable states

A trip can be cancelled from any state except COMPLETED, CANCELLED, or FAILED. Attempting to cancel a completed trip returns 400

Reason code required

Driver cancellation rate

If the cancelling party is the driver and the trip was in DRIVER_ASSIGNED or later state, this cancellation is recorded in the driver’s behavioral score

Passenger no-show

When reason is NO_SHOW and the trip was in DRIVER_ARRIVED state, the driver may be eligible for a waiting time fee depending on operator policy

Refunds

Cancellations before DRIVER_ASSIGNED receive a full refund. Post-assignment cancellations may be subject to a cancellation fee per operator configuration

4.4.5. Get Trip Details

GET /api/v1/trips/{tripId}

Returns the full current state of a trip at the moment of the call. This is the canonical source of truth for a trip’s status, fare data, assignment details, and scheduling configuration. Both driver and passenger apps poll this endpoint to refresh trip state, though real-time status changes are also pushed via the notification service to reduce polling frequency.

The response includes both estimatedFare (computed at booking time) and actualFare (computed at completion). Before the trip completes, actualFare will be null. After completion, both values are present for fare comparison and dispute resolution.

403

Verify authentication and permissions

4.4.6. Get Passenger Trip History

GET /api/v1/trips/user/{userId}

Returns all trips ever associated with a passenger account — completed, cancelled, scheduled, and in-progress — ordered newest first. The response is not paginated; for passengers with very large trip histories, clients should consider filtering by date range on the client side.

This endpoint is used to build trip history screens in the passenger app, generate user-level audit trails for support investigations, and produce ridership reports for regulatory submissions.

5. Driver & Vehicle Management API

Base URL: http://localhost:10001

The Driver & Vehicle API is the authoritative registry for every human and machine that operates on the Tanzim network. It is a multi-domain service — rather than a single narrow responsibility, it owns the full scope of fleet governance: who is allowed to drive, which vehicle they operate, when they are working, how passengers have rated them, and whether their conduct meets the platform’s safety and compliance standards.

This service is designed to serve three distinct consumer groups simultaneously. Driver apps use it for authentication, shift management, location updates, and viewing their own performance data. Passenger apps use it indirectly — the dispatch engine queries driver availability and proximity data here before assigning a trip. Fleet operators and compliance teams use the administrative endpoints for driver onboarding, licence monitoring, suspension management, and regulatory reporting.

The service integrates with Keycloak for identity management. Every driver registration provisions a Keycloak account, and all driver-facing JWT tokens are issued and validated through that identity provider. The Driver Service holds the Tanzim-specific profile data (operator assignment, licence details, vehicle assignment, behavioral scores) while Keycloak holds the authentication credentials.

Driver conduct is governed through three layered systems that feed into each other: the shift system tracks working hours and break compliance; the rating system captures passenger-reported service quality; and the behavioral scoring system synthesises telemetry data (speeding, harsh braking, phone use) with operational metrics (cancellation rate, acceptance rate, on-time pickups) into a single composite score. Together these systems give fleet managers and compliance officers a 360-degree view of every driver on the network.

5.4. Shift Management Endpoints

A driver shift represents a single bounded work period on the Tanzim network. Shifts enforce regulatory fatigue management rules: each shift runs for a maximum of 12 hours, within which the driver is entitled to a total of 90 minutes of rest breaks, with no individual break exceeding 15 minutes. These limits are enforced server-side — the platform will auto-cap overlong breaks and reject break requests once the allowance is exhausted.

Shifts are the primary unit of record for payroll, regulatory hour submissions, and driver fatigue compliance. Every minute of a shift is classified as either net driving time (available for trips) or break time (rest). The shift report endpoint exposes both figures for each shift.

The shift system is also coupled to behavioral scoring: a driver who violates break duration limits (recorded as a BREAK_MAX_TIME_VIOLATED event) accumulates a penalty against their compliance score. Shifts that end with an open break (driver forgot to end it) have the break automatically closed at shift-end time, and the excess is capped.

5.4.1. Shift Business Rules

Rule Detail

Shift duration

Fixed at 12 hours. The shift end time is tracked but not auto-enforced — a shift that overruns 12 hours remains open until explicitly ended. Operations managers receive an alert when a shift exceeds its window

Maximum total break time

90 minutes per shift. Once this threshold is reached, the breakAllowanceExhausted flag is set to true and no further breaks can be started for the remainder of the shift

Maximum single break duration

15 minutes per break. If the driver ends a break after more than 15 minutes, the platform records the end time as startTime + 15 minutes. The actual clock time the driver spent on break does not extend the allowance beyond the cap

Concurrent breaks

Not permitted. If a driver attempts to start a break while one is already in progress, the request is rejected with 409

Concurrent active shifts

A driver can only have one active shift at any time. Starting a shift while one is active returns 409. Operators must end the previous shift before a new one can begin

Break during a trip

The platform does not prevent a driver from starting a break while they have an active trip — this is intentional, as the driver may need to pause for a brief stop. However, starting a break while IN_PROGRESS on a trip is recorded in the event log for compliance review

Auto-close on shift end

If the driver ends their shift while a break is still open, the break is automatically closed at the shift-end timestamp before the shift is finalised

6. Telemetry API

Base URL: http://localhost:10002

The Telemetry Service is the real-time geospatial backbone of the Tanzim dispatch platform. Its primary responsibilities are: ingesting a continuous stream of GPS position updates from thousands of simultaneously active driver devices; maintaining a low-latency geospatial index that the dispatch engine queries to find the nearest eligible driver when a passenger books a trip; and serving live driver positions to passenger apps so riders can watch their driver’s icon move toward the pickup point in real time.

Unlike the other services — which are backed by relational databases and optimised for durable, query-rich data — the Telemetry Service is deliberately designed around an in-memory Redis geospatial store. Driver positions are treated as ephemeral streaming data, not records. Every update overwrites the previous position for that driver. The geospatial index is rebuilt from live pings, not from persisted history. This architecture allows the service to sustain write throughput far beyond what a relational database could handle at GPS ping frequency across a large active fleet.

The service exposes two categories of endpoints: ingestion endpoints (high-frequency writes from the driver app) and query endpoints (reads by the dispatch engine, passenger app, and operations dashboard). These two categories have very different traffic patterns and the API is designed accordingly — the simple coordinate ping endpoint (/update/simple) is as lightweight as possible to minimise the cost of thousands of concurrent writes per second.

Driver App (every 4-10s)
    │

    │
    ▼
Redis Geospatial Index
    │

6.2. Location Update Strategy

The service provides two update paths because driver apps need to send GPS pings very frequently but do not change their full state on every ping. Sending a full state payload at GPS frequency would waste bandwidth and increase processing load unnecessarily.

7. Pricing API

Base URL: http://localhost:10003

The Pricing Service is the financial calculation engine of the Tanzim platform. It is responsible for two distinct but related tasks: generating the fare estimate shown to a passenger before they book, and computing the actual fare charged at trip completion. These are not the same calculation — the estimate is a projection based on the planned route, while the actual fare is computed from the GPS coordinates the driver submitted during the trip.

The pricing model is deliberately layered. A base rate applies to every trip, but multiple overlapping factors can modify it. A trip that departs from an airport special zone, travels through a toll gate, and is booked during the morning peak hour will have contributions from zone pricing, toll charges, and time-window pricing all applied simultaneously. The pricingFactors array in every estimate response makes this composition fully transparent — every factor that affected the fare is listed with its value and impact.

This transparency is important for passenger trust and for dispute resolution. When a passenger questions their fare, the support team can retrieve the estimate response and point to exactly which factors were applied and why.

The service also manages the configuration objects that define those factors: pricing zones (geofenced areas with rate overrides), toll gates (physical infrastructure with time-based charges), and time windows (scheduling rules that define peak, off-peak, and late-night rate periods). Each of these configuration types has its own CRUD API and can be toggled on/off independently without disrupting other pricing rules.

7.1. Fare Calculation Formula

Step 1 — Base components:
    subtotal = onboardingFare
             + (distanceKm × perKmRate)
             + (durationMinutes × perMinuteRate)

Step 2 — Add fixed charges:
    subtotal = subtotal + tollCharges + bookingFee + serviceTax

Step 3 — Apply minimum fare floor:
    subtotal = max(subtotal, minimumFare)

Step 4 — Apply surge multiplier:
    totalFare = subtotal × surgeMultiplier

The perKmRate, onboardingFare, and perMinuteRate used in Step 1 are sourced from whichever pricing configuration takes priority: zone pricing overrides time-window pricing, which overrides the base rate. The highest-priority matching configuration wins.

2

7.3. Pricing Zones

Zones are polygon-defined geographic areas that override the base per-km and onboarding fare rates within their boundaries. When the pickup point or destination of a trip falls within a zone, that zone’s rates are applied instead of the default time-window or base rates. If both pickup and destination are in different zones, the zone with the higher priority value wins.

Zones are stored as closed polygons — the coordinate array must define at least 3 vertices. The platform automatically closes the polygon (connecting the last vertex back to the first) if the final coordinate is not identical to the first.

7.4. Toll Gates

Toll gates represent physical road toll collection points on routes within the Tanzim operating area. When the platform calculates a fare estimate, it traces the planned route and checks each toll gate’s polygon to determine whether the route passes through any managed toll infrastructure. Every toll gate detected on the route contributes its charge — based on vehicle type and time of day — to the tollCharges component of the fare.

Toll gate polygons are typically narrow rectangles positioned perpendicular to the road at the toll point, sized to capture the road footprint while excluding adjacent areas. Each toll gate has a unique code (e.g. SZR-TG-03) used for integration with external toll management systems.

7.5. Time Windows

Time windows define the pricing periods that apply across the operating day. They are the mechanism through which Tanzim implements peak-hour pricing, late-night incentive rates, and weekend flat rates. At the moment a fare estimate is generated, the platform looks up which time window (if any) is active for the given vehicle type at the requested departure time, and applies that window’s rates in place of the default base rate.

Each time window is specific to a single vehicle type — there is no cross-type shorthand. To configure peak pricing for both SEDAN and SUV, two separate time window records must be created. Windows can overlap on the clock (e.g. a REGULAR window from 09:00–18:00 and a PEAK window from 07:00–09:00) — the priority field determines which window wins when overlap occurs.

7.6. Fare Estimation Endpoints

7.6.1. Calculate Price Estimate

POST /api/v1/pricing/estimate

The primary pre-trip fare estimation endpoint. Given a pickup point, destination, and vehicle type, the engine executes the full pricing pipeline:

  1. Queries the mapping integration to calculate route distance (km) and estimated travel time (minutes) for the given coordinates

  2. Checks the pickup and destination points against all active pricing zones to identify any zone-based rate overrides

  3. Determines which time window (if any) is active for this vehicle type at the current time

  4. Traces the planned route against all active toll gate polygons to identify any gates on the path

  5. Applies zone or time-window rate overrides — zone pricing takes precedence over time-window pricing

  6. Computes the fare components: onboarding fare, distance fare, time fare, toll charges, booking fee, and service tax

  7. Applies the minimum fare floor

  8. Applies any active surge multiplier for the pickup zone

  9. Returns the total fare, a min/max fare range, and a full breakdown of every applied factor

The returned estimateId should be stored by the client and passed when creating a trip booking. The Trip Service uses this ID to record which estimate the passenger was shown at booking time. Estimates expire — typically after 10 minutes — and a new estimate must be generated if booking is delayed.

Returns a detailed line-item breakdown for a route where the distance and travel time are already known. 7.6.5. Get Actual Fare Breakdown (Post-Trip)

Computes the definitive post-trip fare from the GPS coordinates the driver submitted during the trip. This is the amount that will be charged to the passenger. The coordinates parameter should be the same coordinate array passed to POST /trips/{tripId}/complete.

The actual fare may differ from the pre-trip estimate for three reasons: the driver may have taken a longer or shorter route than the planned path; the actual trip duration may differ from the estimated duration; or the driver may have passed through different toll gates than were predicted on the planned route.

7.7. Surge Pricing Endpoints

7.7.1. Get Current Surge Multiplier

GET /api/v1/pricing/surge?vehicleType={type}

Returns the active surge multiplier for a vehicle type at the current moment. A multiplier of 1.0 means no surge — fares are at standard rates. Values above 1.0 indicate that demand in the area is outpacing driver supply and fares have been elevated to attract more drivers online and moderate demand.

Surge conditions are evaluated in real time by comparing the count of available drivers in each pricing zone against the rate of incoming trip requests. The multiplier, the zone(s) driving the surge, and the reason string are all returned so the passenger-facing UI can display a meaningful explanation.
